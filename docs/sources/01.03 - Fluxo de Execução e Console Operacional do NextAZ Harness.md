# 01.03 - Fluxo de Execução e Console Operacional do NextAZ Harness


## Objetivo


Definir o fluxo operacional do NextAZ Harness, a necessidade de um console administrativo e a estratégia inicial de implantação em VPS.


O NextAZ Harness deve ser tratado como uma plataforma interna de execução, governança e orquestração de IA. Ele não é uma aplicação final voltada diretamente ao cliente. Os produtos NextAZ — Cartório, Funcionário Digital, CRM, ERP e futuras verticais — consomem suas capacidades.


> Regra central: modelos, frameworks e providers são componentes substituíveis. O Harness é a camada estável que controla execução, contexto, tools, conhecimento, políticas, segurança, auditoria e observabilidade.


## 1. O Harness terá tela?


Sim, mas a tela do Harness deve ser um **console operacional e administrativo**, e não um produto final para clientes.


No MVP, o Harness deve continuar sendo **API-first**. O console existe para dar visibilidade e governança à equipe NextAZ.


A princípio, o console será de uso interno da NextAZ. No futuro, partes específicas podem ser expostas para administradores de tenants, como gestão de base de conhecimento, configurações de agentes ou métricas.


## 2. Objetivos do Console Operacional


O console deve permitir:


- visualizar a saúde geral do Harness;
- acompanhar execuções de agentes;
- consultar erros e falhas;
- identificar qual modelo/provider foi utilizado;
- visualizar tools executadas;
- acompanhar custo e latência;
- gerenciar Agent Definitions e versões;
- visualizar Tools e Capabilities registradas;
- configurar Model Policies;
- acompanhar Knowledge Bases e documentos indexados;
- gerenciar configurações por tenant;
- visualizar eventos, filas e falhas de processamento;
- consultar auditoria;
- habilitar ou desabilitar funcionalidades com segurança.


O console não deve permitir acesso direto e irrestrito a dados de negócio pertencentes aos produtos externos.


## 3. Estrutura inicial do Console


### 3.1 Dashboard


Exibir inicialmente:


- execuções nas últimas 24 horas;
- execuções concluídas;
- execuções com erro;
- tempo médio de resposta;
- custo estimado por provider/modelo;
- tools mais chamadas;
- agentes mais utilizados;
- tenants ativos;
- status de PostgreSQL, RabbitMQ e providers;
- alertas operacionais.


### 3.2 Executions


Tela central para rastreamento das execuções.


Campos mínimos:


- ExecutionId;
- CorrelationId;
- TenantId;
- AgentId;
- AgentVersion;
- Channel;
- Operation;
- Status;
- Provider;
- Model;
- StartAt;
- EndAt;
- Duration;
- EstimatedCost;
- ErrorCode;
- CreatedAt.


Ao abrir uma execução, exibir uma timeline de passos:


1. request recebida;
2. tenant resolvido;
3. agente resolvido;
4. policies avaliadas;
5. contexto carregado;
6. knowledge retrieval executado;
7. model route resolvida;
8. runtime iniciado;
9. tools chamadas;
10. resposta produzida;
11. eventos publicados;
12. execução finalizada.


O console não deve exibir segredos, tokens ou credenciais.


### 3.3 Agents


Permitir visualizar:


- AgentId;
- nome;
- objetivo;
- vertical;
- versão ativa;
- status;
- ModelPolicy;
- MemoryPolicy;
- KnowledgeBase padrão;
- tools autorizadas;
- tenants com o agente habilitado.


No MVP, alterações críticas de agente podem permanecer via configuração/backend. A tela inicialmente pode ser principalmente de consulta.


### 3.4 Tools e Capabilities


Exibir:


- ToolId;
- descrição;
- categoria;
- timeout;
- política de retry;
- quais agentes podem utilizá-la;
- status;
- versão;
- tipo de integração.


Exemplos:


- cartorio.buscar-protesto;
- cartorio.criar-pedido;
- billing.verify-payment;
- documents.extract-payment-receipt;
- messaging.send-whatsapp;
- knowledge.search.


### 3.5 Model Policies


O console deve exibir políticas abstratas, e não obrigar agentes a conhecer modelos concretos.


Exemplos:


- fast-cheap;
- balanced;
- high-reasoning;
- vision;
- extraction.


Cada política poderá apontar para:


- provider principal;
- modelo principal;
- fallbacks;
- limite de custo;
- timeout;
- limites por tenant;
- configuração de temperatura quando aplicável.


### 3.6 Knowledge Bases


Permitir acompanhar:


- KnowledgeBaseId;
- TenantId;
- nome;
- quantidade de documentos;
- quantidade de chunks;
- status de indexação;
- última atualização;
- modelo de embedding utilizado;
- erros de processamento.


O arquivo original deve permanecer em Storage. O PostgreSQL + pgvector armazena os metadados, chunks e embeddings necessários para retrieval.


### 3.7 Tenants


Exibir apenas configurações pertencentes ao Harness:


- TenantId;
- status;
- agentes habilitados;
- tools habilitadas;
- Model Policies permitidas;
- Knowledge Bases;
- limites de uso;
- features habilitadas.


O Harness não deve duplicar CRM, ERP ou dados de domínio específicos dos produtos.


### 3.8 Eventos e filas


Permitir visualizar de forma operacional:


- eventos processados;
- mensagens pendentes;
- retries;
- dead-letter queue;
- erros recorrentes;
- consumers ativos.


Nenhum botão de reprocessamento deve existir sem proteção contra duplicidade e idempotência.


## 4. Autenticação e autorização do Console


O console deve utilizar a autenticação central da NextAZ/ALF.


Não criar um login paralelo específico para o Harness.


O backend deve determinar:


- UserId;
- TenantId quando aplicável;
- roles;
- permissions.


Perfis iniciais sugeridos:


- HarnessAdmin: administração completa da plataforma;
- HarnessOperator: operação, execução, observabilidade e reprocessamentos controlados;
- HarnessViewer: somente leitura.


Toda ação administrativa relevante deve ser auditada.


### Regras obrigatórias de segurança


- Nunca confiar em TenantId informado livremente pelo front-end.
- Nunca armazenar API keys no navegador.
- Nunca retornar secrets completos ao front-end.
- Credenciais de providers devem ficar apenas no backend/secret store.
- O console deve aplicar autorização no backend, e não apenas esconder elementos visuais.
- Logs devem evitar exposição desnecessária de CPF, CNPJ, documentos e dados sensíveis.
- Dados sensíveis devem ser mascarados quando possível.
- Operações destrutivas ou críticas devem exigir permissão específica.


## 5. Fluxo geral de execução


Fluxo conceitual obrigatório:


HarnessRequest
→ autenticação/autorização
→ resolução do Tenant
→ construção do ExecutionContext
→ Agent Resolver
→ carregamento da AgentDefinition/AgentVersion
→ carregamento da TenantAgentConfiguration
→ avaliação de Policies
→ carregamento de memória e contexto
→ Knowledge Retrieval quando aplicável
→ Model Router
→ resolução de provider/modelo
→ Agent Runtime
→ Tool Registry
→ validação de permissão da Tool
→ execução da Tool
→ continuação da execução
→ resposta
→ persistência de telemetria
→ publicação de eventos
→ conclusão.


## 6. Falhas e resiliência


Toda execução deve possuir estados claros, por exemplo:


- Pending;
- Running;
- WaitingExternalEvent;
- Completed;
- Failed;
- Cancelled;
- TimedOut.


O Harness deve tratar:


- timeout do modelo;
- indisponibilidade de provider;
- fallback de modelo;
- timeout de tool;
- retry de integrações quando seguro;
- redelivery do RabbitMQ;
- duplicidade de evento;
- falha de retrieval;
- indisponibilidade de PostgreSQL;
- falhas temporárias externas.


Retries nunca podem executar novamente operações não idempotentes sem proteção explícita.


## 7. Deployment inicial


### Decisão atual


O deployment do NextAZ Harness será realizado diretamente em uma **VPS**.


O desenho inicial deve ser simples, containerizado e preparado para crescer sem criar dependência desnecessária de cloud específica.


### Topologia inicial sugerida


Internet
→ Reverse Proxy (Nginx ou Traefik)
→ NextAZ Harness API
→ NextAZ Harness Workers
→ PostgreSQL + pgvector
→ RabbitMQ
→ Redis opcional


Providers externos são consumidos por saída HTTPS:


- OpenAI;
- Gemini;
- Anthropic;
- outros providers futuros.


### Containers sugeridos


- nextaz-harness-api;
- nextaz-harness-worker;
- nextaz-harness-console;
- postgres-pgvector;
- rabbitmq;
- redis, caso necessário;
- reverse-proxy.


Pode ser utilizado Docker Compose inicialmente.


### Regras de infraestrutura para a VPS


- PostgreSQL não deve ficar exposto publicamente;
- RabbitMQ Management não deve ficar aberto à internet sem proteção;
- somente reverse proxy deve expor portas públicas necessárias;
- utilizar HTTPS;
- secrets devem ficar fora do repositório;
- utilizar volumes persistentes;
- configurar backup do PostgreSQL;
- configurar retenção de logs;
- health checks em API e workers;
- restart policy nos containers;
- migration do banco controlada no deployment;
- firewall da VPS configurado;
- acesso SSH restrito;
- não utilizar senha padrão em nenhum serviço.


## 8. Deploy pipeline inicial


Fluxo sugerido para o primeiro estágio:


Git repository
→ build/test
→ Docker image
→ push para registry
→ VPS
→ docker compose pull
→ migrations
→ docker compose up -d
→ health check.


O processo pode começar manual/semi-automatizado e evoluir posteriormente para CI/CD completo.

## 10. Decisão arquitetural sobre a interface do Harness


O Harness deve possuir console próprio, mas esse console não substitui as interfaces dos produtos NextAZ.


Exemplo:


- Cartório NextAZ possui sua própria experiência de usuário;
- Funcionário Digital possui sua própria experiência;
- ERP possui sua própria experiência;
- CRM possui sua própria experiência;
- Harness Console é a experiência operacional da plataforma de IA.


No primeiro MVP, recomenda-se implementar inicialmente:


1. Dashboard;
2. Executions;
3. Execution Detail/Timeline;
4. Agents;
5. Tools;
6. Knowledge Bases;
7. Model Policies;
8. Tenants;
9. Health/Status.


Configurações destrutivas e edição avançada podem ser adicionadas gradualmente.


## Resultado esperado


Ao final dessa fase, o NextAZ Harness terá uma fronteira clara entre:


- plataforma de IA;
- produtos de negócio;
- console operacional;
- infraestrutura;
- providers externos;
- dados dos tenants.


A tela do Harness existe para governança e operação. Ela não deve se transformar em um novo CRM, ERP ou produto vertical.
