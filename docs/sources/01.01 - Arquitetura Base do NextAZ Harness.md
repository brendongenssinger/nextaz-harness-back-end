# 01.01 - Arquitetura Base do NextAZ Harness


## Objetivo


Definir a arquitetura base do NextAZ Harness como camada central de orquestração de inteligência artificial da plataforma NextAZ.


O Harness não representa uma vertical de negócio específica. Cartório, imobiliária, CRM, ERP, cobrança, follow-up, prospecção e demais produtos consomem suas capacidades. O objetivo é desacoplar agentes, modelos, providers, memória, ferramentas, políticas e execução das regras de negócio específicas de cada domínio.


## Princípio central


> O modelo sugere, o Harness controla e o domínio decide.


Regras determinísticas e sensíveis não podem depender da decisão de um LLM. Exemplos: confirmação de pagamento, autorização de acesso, mudança de status financeiro, emissão definitiva de documentos, permissões e regras legais.


## Papel do Harness


O NextAZ Harness deve:


- receber solicitações, mensagens ou eventos;
- identificar o tenant responsável pela execução;
- montar o contexto de execução;
- resolver qual agente deve atuar;
- carregar a configuração do agente;
- validar policies e ferramentas permitidas;
- definir a política de modelo adequada;
- delegar a escolha do provider/modelo ao Model Router;
- carregar memória e conhecimento quando necessário;
- executar o agente através de uma abstração de runtime;
- registrar telemetria, custo, latência, uso de tools e resultado;
- publicar eventos de saída quando necessário.


## Contexto obrigatório de execução


Toda execução do Harness deve possuir, no mínimo:


- TenantId
- AgentId
- AgentVersion
- ExecutionId
- CorrelationId
- Channel
- Operation


Esses identificadores devem atravessar todas as camadas relevantes e estar presentes na observabilidade e nos eventos publicados.


## AgentId


AgentId representa uma capacidade de negócio estável. Ele nunca deve representar provider, modelo ou framework.


Exemplos corretos:


- cartorio.atendimento
- cartorio.certidao
- cartorio.cancelamento-protesto
- imobiliaria.atendimento
- imobiliaria.qualificacao-lead
- crm.followup
- cobranca.negociacao
- prospeccao.outbound


Exemplos proibidos:


- GPTAgent01
- ClaudeAgent
- GeminiAgent
- SemanticKernelAgent


## AgentVersion


Cada configuração de agente deve ser versionada. A versão permite evoluir prompt, tools, policies e comportamento sem perder rastreabilidade das execuções anteriores.


Exemplo:


AgentId: cartorio.cancelamento-protesto
AgentVersion: 1


## ExecutionId


Cada execução individual recebe um identificador único. Ele deve permitir rastrear toda a cadeia de execução, incluindo:


- mensagem recebida;
- agente selecionado;
- modelo utilizado;
- tools chamadas;
- eventos publicados;
- erros;
- tempo de execução;
- custo estimado.


## Catálogo de agentes


O Harness deve possuir um Agent Registry ou Agent Catalog.


Exemplo conceitual:


NextAZ Harness


Agent Registry
├── cartorio.atendimento
├── cartorio.certidao
├── cartorio.cancelamento-protesto
├── imobiliaria.atendimento
├── imobiliaria.qualificacao-lead
├── crm.followup
├── cobranca.negociacao
└── prospeccao.outbound


Cada agente deve possuir configuração semelhante a:


{
  "agentId": "cartorio.cancelamento-protesto",
  "vertical": "cartorio",
  "objective": "Conduzir o processo de solicitação de cancelamento de protesto",
  "modelPolicy": "balanced",
  "memoryPolicy": "customer-context",
  "requiresTenantContext": true,
  "allowedTools": [
    "cartorio.buscar-protesto",
    "cartorio.criar-pedido",
    "billing.gerar-link-pagamento",
    "billing.consultar-pagamento"
  ]
}


## Multi-tenancy


O mesmo AgentId deve poder ser reutilizado por múltiplos tenants.


Não criar um agente específico por cliente quando a capacidade de negócio é a mesma.


Evitar:


- cartorio-goiania-agent
- cartorio-anapolis-agent
- cartorio-brasilia-agent


Preferir:


- cartorio.cancelamento-protesto


As diferenças devem ser controladas por TenantAgentConfiguration.


Campos sugeridos:


- TenantId
- AgentId
- Enabled
- Instructions
- AllowedTools
- KnowledgeBaseId
- ModelPolicy
- MemoryPolicy
- Limits
- ConfigurationVersion


## Agent Resolver


Canais e serviços externos não devem decidir diretamente qual implementação de IA executar.


Exemplo de entrada:


HarnessRequest
{
  TenantId,
  Channel,
  Operation,
  Content,
  CorrelationId
}


Fluxo esperado:


Tenant
→ Canal
→ Contexto
→ Operação/Intenção
→ Agent Resolver
→ AgentId
→ Agent Policy
→ Model Router
→ Tools autorizadas
→ Runtime
→ Resultado


## Tool Registry


As ferramentas devem ser registradas e identificadas por IDs estáveis.


Exemplos:


- cartorio.buscar-protesto
- cartorio.criar-pedido
- billing.gerar-link-pagamento
- billing.consultar-pagamento
- crm.buscar-contato
- crm.atualizar-contato


Nenhum agente pode executar uma tool que não esteja explicitamente autorizada para:


1. o AgentId;
2. o TenantId;
3. o contexto da execução.


O agente nunca deve acessar diretamente banco de dados de outro domínio.


## Model Router


AgentId não deve estar acoplado a um modelo específico.


Exemplo:


AgentId: cartorio.atendimento
ModelPolicy: fast-cheap


AgentId: cartorio.analise-complexa
ModelPolicy: high-reasoning


O Model Router deve receber uma política e resolver provider/modelo em tempo de execução com base em critérios como:


- qualidade;
- custo;
- latência;
- disponibilidade;
- limites do tenant;
- tipo de tarefa;
- fallback.


O Harness deve suportar providers como OpenAI, Gemini, Anthropic ou outros sem alterar o domínio do agente.


## Runtime de agentes


O restante da plataforma não deve depender diretamente do Semantic Kernel.


Criar abstração própria, por exemplo:


IAgentRuntime


A implementação inicial pode utilizar Semantic Kernel, mas esse detalhe deve permanecer atrás da abstração.


Objetivo:


Hoje:
IAgentRuntime → Semantic Kernel


Futuro:
IAgentRuntime → outro framework/runtime


A troca não deve exigir reescrever agentes, verticais ou serviços de negócio.


## Regra de dependência


Nenhum serviço de negócio deve chamar diretamente:


- OpenAI SDK;
- Gemini SDK;
- Anthropic SDK;
- Semantic Kernel;
- LangChain;
- qualquer provider específico.


Toda execução de IA deve passar pelas abstrações do Harness.


## Memória e conhecimento


O Harness deve oferecer abstrações para memória e recuperação de conhecimento.


A implementação atual pode utilizar PostgreSQL + pgvector.


A memória deve respeitar TenantId e não pode haver mistura de contexto entre clientes.


Separar conceitualmente:


- memória de conversa;
- memória operacional;
- base de conhecimento;
- histórico do CRM;
- estado determinístico do domínio.


Dados críticos de negócio não devem depender exclusivamente de memória vetorial.


## RabbitMQ e eventos


RabbitMQ deve ser utilizado para integração assíncrona e eventos de domínio quando fizer sentido.


O Harness pode consumir eventos e publicar novos eventos, mas não deve assumir propriedade sobre regras de domínio externas.


Exemplo do cartório:


WhatsApp
→ HarnessRequest
→ Agent Resolver
→ cartorio.cancelamento-protesto
→ Tool: cartorio.buscar-protesto
→ Tool: cartorio.criar-pedido
→ Tool: billing.gerar-link-pagamento
→ aguarda confirmação determinística de pagamento
→ evento PaymentConfirmed
→ serviço de domínio libera próxima etapa
→ Harness pode continuar comunicação com o cliente


A confirmação do pagamento não pode ser inferida pelo LLM.


## Estrutura lógica inicial da solução .NET


Sugestão inicial:


NextAZ.Harness.Api
NextAZ.Harness.Application
NextAZ.Harness.Domain
NextAZ.Harness.Contracts
NextAZ.Harness.Infrastructure
NextAZ.Harness.Runtime
NextAZ.Harness.Providers
NextAZ.Harness.Observability


### NextAZ.Harness.Domain


Contém conceitos centrais independentes de infraestrutura:


- AgentDefinition
- AgentId
- AgentVersion
- ModelPolicy
- ToolDefinition
- ToolPermission
- ExecutionContext
- TenantAgentConfiguration


Não deve referenciar Semantic Kernel nem SDKs de providers.


### NextAZ.Harness.Application


Contém casos de uso e orquestração:


- ExecuteHarnessRequest
- ResolveAgent
- ValidateAgentPolicy
- BuildExecutionContext
- ExecuteAgent


### NextAZ.Harness.Contracts


Contém contratos públicos utilizados por outros serviços:


- HarnessRequest
- HarnessResponse
- eventos publicados;
- mensagens de integração.


### NextAZ.Harness.Runtime


Contém abstrações e implementações do runtime de agentes.


Interfaces sugeridas:


- IAgentRuntime
- IAgentResolver
- IAgentRegistry
- IToolRegistry
- IModelRouter
- IMemoryProvider
- IExecutionPolicyEvaluator


### NextAZ.Harness.Providers


Contém adaptadores de providers de IA.


Exemplo:


- OpenAIModelProvider
- GeminiModelProvider
- AnthropicModelProvider


Nenhum provider deve vazar seus tipos específicos para Domain ou Application.


### NextAZ.Harness.Infrastructure


Responsável por persistência, RabbitMQ, PostgreSQL, pgvector, cache e integrações técnicas.


### NextAZ.Harness.Observability


Responsável por logs estruturados, métricas, tracing, custo e auditoria das execuções.


## Regras obrigatórias para implementação pelo Codex


1. Não acoplar AgentId a provider ou modelo.
2. Não permitir chamadas diretas a LLM fora da camada de providers/runtime do Harness.
3. Não permitir tool fora da lista autorizada por agente e tenant.
4. TenantId deve estar presente em toda execução.
5. Toda execução deve possuir CorrelationId e ExecutionId.
6. Regras determinísticas permanecem nos serviços de domínio.
7. Semantic Kernel é detalhe de implementação, não contrato público.
8. Providers devem ser substituíveis.
9. Memória deve ser isolada por tenant.
10. Domínios externos permanecem donos de seus próprios dados.
11. O Harness não deve acessar tabelas de negócio diretamente quando existir um serviço/API responsável pelo domínio.
12. Toda execução deve ser observável e auditável.


## Resultado esperado


A arquitetura deve permitir que a NextAZ crie novas verticais e novos agentes sem duplicar infraestrutura de IA.


Exemplo:


Cartório
Imobiliária
CRM
ERP / Marketplaces
Cobrança
Follow-up
Prospecção
Professor Digital


Todos devem reutilizar:


- Agent Registry;
- Agent Resolver;
- Model Router;
- Tool Registry;
- Runtime;
- memória;
- policies;
- observabilidade;
- infraestrutura multi-tenant.


O diferencial do NextAZ Harness não é simplesmente consumir uma API de IA. É controlar como modelos, agentes, memória, ferramentas, regras de negócio e integrações operam em conjunto dentro da plataforma NextAZ.
