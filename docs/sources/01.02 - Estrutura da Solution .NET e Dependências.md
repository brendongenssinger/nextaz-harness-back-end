# 01.02 - Estrutura da Solution .NET e Dependências


## Objetivo


Definir a estrutura física da solution .NET do NextAZ Harness, as responsabilidades de cada projeto, as dependências permitidas e proibidas e as abstrações mínimas que o Codex deve respeitar na implementação.


Este documento complementa o 01.01. A regra principal continua sendo:


> O modelo sugere, o Harness controla e o domínio decide.


A estrutura deve permitir trocar providers de IA, framework de agentes, mecanismo de memória e integrações técnicas sem reescrever os domínios de negócio da NextAZ.


## Princípios de arquitetura


1. Dependências devem apontar para dentro, nunca para detalhes de infraestrutura.
2. Domain não conhece Semantic Kernel, OpenAI, Gemini, Anthropic, RabbitMQ, PostgreSQL, pgvector ou qualquer SDK externo.
3. Application orquestra casos de uso e depende de abstrações, não de implementações concretas.
4. Contracts contém contratos públicos de integração e não pode depender de Runtime, Infrastructure ou Providers.
5. Runtime define a abstração de execução de agentes e os componentes de resolução, registry, policies e routing.
6. Providers contém adaptadores concretos para modelos e provedores de IA.
7. Infrastructure contém persistência, mensageria, cache, memória vetorial e integrações técnicas.
8. Api é o composition root HTTP e não deve conter regra de negócio.
9. Regras determinísticas continuam nos serviços de domínio externos ao Harness.
10. Toda execução deve carregar TenantId, ExecutionId e CorrelationId.


## Estrutura recomendada da solution


```text
NextAZ.Harness.sln
│
├── src
│   ├── NextAZ.Harness.Api
│   ├── NextAZ.Harness.Application
│   ├── NextAZ.Harness.Domain
│   ├── NextAZ.Harness.Contracts
│   ├── NextAZ.Harness.Runtime
│   ├── NextAZ.Harness.Providers
│   ├── NextAZ.Harness.Infrastructure
│   └── NextAZ.Harness.Observability
│
└── tests
    ├── NextAZ.Harness.Domain.Tests
    ├── NextAZ.Harness.Application.Tests
    ├── NextAZ.Harness.Runtime.Tests
    ├── NextAZ.Harness.Infrastructure.Tests
    └── NextAZ.Harness.IntegrationTests
```


O Codex deve manter cada responsabilidade isolada. Não mover tipos entre projetos apenas por conveniência.


## 1. NextAZ.Harness.Domain


Projeto mais interno e estável da solution.


Responsabilidades:


- entidades e value objects do Harness;
- regras invariantes do próprio Harness;
- identidade e versionamento de agentes;
- definições de tools;
- políticas conceituais;
- contexto de execução;
- configuração multi-tenant do agente.


Tipos iniciais sugeridos:


```text
AgentId
AgentVersion
AgentDefinition
ToolId
ToolDefinition
ToolPermission
ModelPolicy
MemoryPolicy
ExecutionContext
ExecutionId
TenantAgentConfiguration
AgentExecutionStatus
```


Exemplo conceitual de ExecutionContext:


```csharp
public sealed record ExecutionContext(
    Guid TenantId,
    string AgentId,
    int AgentVersion,
    Guid ExecutionId,
    string CorrelationId,
    string Channel,
    string Operation);
```


Regras:


- não referenciar nenhum SDK externo de IA;
- não referenciar EF Core;
- não referenciar RabbitMQ;
- não referenciar Semantic Kernel;
- não conhecer HTTP, controllers ou bancos de dados.


Dependências permitidas:


```text
Domain -> nenhuma camada interna da solution
```


## 2. NextAZ.Harness.Contracts


Responsável pelos contratos públicos compartilhados com outros serviços da NextAZ.


Tipos sugeridos:


```text
HarnessRequest
HarnessResponse
HarnessError
HarnessExecutionStarted
HarnessExecutionCompleted
HarnessExecutionFailed
AgentInvocationRequested
ToolInvocationCompleted
```


Exemplo conceitual:


```csharp
public sealed record HarnessRequest(
    Guid TenantId,
    string Channel,
    string Operation,
    string Content,
    string CorrelationId,
    IReadOnlyDictionary<string, string>? Metadata = null);
```


Contracts deve ser pequeno e estável.


Não colocar em Contracts:


- classes do Semantic Kernel;
- DTOs de OpenAI/Gemini/Anthropic;
- entidades do EF Core;
- models internos de persistência;
- detalhes de RabbitMQ;
- prompts internos.


Dependências permitidas:


```text
Contracts -> nenhuma camada de infraestrutura
```


## 3. NextAZ.Harness.Application


Responsável pelos casos de uso e pela orquestração da execução.


Casos de uso iniciais sugeridos:


```text
ExecuteHarnessRequest
ResolveAgent
BuildExecutionContext
LoadTenantAgentConfiguration
ValidateExecutionPolicies
ResolveModelPolicy
LoadMemoryContext
ExecuteAgent
PersistExecutionResult
PublishExecutionEvents
```


Interfaces que Application pode consumir:


```text
IAgentResolver
IAgentRegistry
IAgentRuntime
IToolRegistry
IModelRouter
IMemoryProvider
ITenantAgentConfigurationRepository
IExecutionRepository
IExecutionPolicyEvaluator
IEventPublisher
IExecutionTelemetry
```


Application não deve instanciar diretamente implementações concretas.


Exemplo proibido:


```csharp
var kernel = Kernel.CreateBuilder()
    .AddOpenAIChatCompletion(...)
    .Build();
```


Esse código não pertence à Application.


## 4. NextAZ.Harness.Runtime


Runtime representa o mecanismo de execução dos agentes do Harness.


O objetivo é impedir que Semantic Kernel se torne contrato arquitetural da NextAZ.


Interfaces centrais sugeridas:


```csharp
public interface IAgentRuntime
{
    Task<AgentExecutionResult> ExecuteAsync(
        AgentExecutionRequest request,
        CancellationToken cancellationToken);
}
```


```csharp
public interface IAgentResolver
{
    Task<AgentResolutionResult> ResolveAsync(
        HarnessRequest request,
        CancellationToken cancellationToken);
}
```


```csharp
public interface IModelRouter
{
    Task<ModelRoute> ResolveAsync(
        ModelRoutingContext context,
        CancellationToken cancellationToken);
}
```


```csharp
public interface IToolRegistry
{
    Task<IReadOnlyCollection<ToolDefinition>> GetAllowedToolsAsync(
        Guid tenantId,
        string agentId,
        CancellationToken cancellationToken);
}
```


```csharp
public interface IMemoryProvider
{
    Task<MemoryContext> LoadAsync(
        MemoryRequest request,
        CancellationToken cancellationToken);
}
```


Runtime pode conter uma implementação inicial baseada em Semantic Kernel, preferencialmente isolada em namespace/pasta própria:


```text
Runtime/
├── Abstractions
├── AgentResolution
├── ModelRouting
├── Tooling
├── Policies
└── SemanticKernel
```


Se no futuro a NextAZ substituir Semantic Kernel, apenas a implementação deve mudar. Interfaces públicas do Harness devem permanecer estáveis.


## 5. NextAZ.Harness.Providers


Responsável por adaptadores de providers e modelos de IA.


Estrutura sugerida:


```text
Providers/
├── Abstractions
├── OpenAI
├── Gemini
├── Anthropic
└── Configuration
```


Interface conceitual:


```csharp
public interface IModelProvider
{
    string ProviderId { get; }


    Task<ModelExecutionResult> ExecuteAsync(
        ModelExecutionRequest request,
        CancellationToken cancellationToken);
}
```


Cada implementação traduz o contrato interno do Harness para o SDK específico e converte a resposta do provider novamente para tipos internos.


Nunca retornar para Application ou Domain objetos específicos como resposta nativa de OpenAI, Gemini ou Anthropic.


O Model Router resolve uma rota, por exemplo:


```text
ModelPolicy: fast-cheap
        ↓
Provider: Gemini
Model: modelo-configurado
```


ou:


```text
ModelPolicy: high-reasoning
        ↓
Provider: OpenAI
Model: modelo-configurado
```


Os nomes concretos de modelos devem ser configuração operacional, não regra de domínio.


## 6. NextAZ.Harness.Infrastructure


Responsável pelos detalhes técnicos externos ao core.


Subáreas sugeridas:


```text
Infrastructure/
├── Persistence
│   ├── PostgreSql
│   └── Repositories
├── Memory
│   └── PgVector
├── Messaging
│   └── RabbitMq
├── Cache
├── Tenancy
└── Configuration
```


Responsabilidades:


- DbContext e migrations do banco próprio do Harness;
- repositórios;
- persistência das execuções;
- configurações de agentes e tenants;
- armazenamento de memória e embeddings;
- publicação e consumo de eventos RabbitMQ;
- cache;
- secrets/configuração de infraestrutura.


O banco do Harness armazena dados do Harness, por exemplo:


```text
Agents
AgentVersions
TenantAgentConfigurations
AgentTools
Executions
ExecutionSteps
ModelUsages
ToolExecutions
MemoryReferences
Policies
```


Não armazenar como fonte primária dados de negócio que pertencem a CRM, ERP, Cartório, Billing ou outras verticais.


## 7. NextAZ.Harness.Observability


Responsável por observabilidade transversal.


Deve capturar no mínimo:


- TenantId;
- ExecutionId;
- CorrelationId;
- AgentId;
- AgentVersion;
- ProviderId;
- ModelId;
- duração;
- tokens/uso reportado pelo provider;
- custo estimado quando disponível;
- tools executadas;
- erros e retries;
- status final.


Interfaces sugeridas:


```text
IExecutionTelemetry
IModelUsageTracker
IToolExecutionTracker
IAuditWriter
```


Não registrar conteúdo sensível integralmente por padrão. Logs devem suportar mascaramento e políticas de retenção.


## 8. NextAZ.Harness.Api


Responsável apenas pela borda HTTP e composition root.


Pode conter:


- endpoints/controllers;
- autenticação/autorização;
- validação de request de transporte;
- DI;
- health checks;
- OpenAPI;
- middleware de correlation id;
- configuração de tracing.


Não pode conter:


- prompt de agente;
- regra de seleção de modelo;
- regra de negócio do cartório;
- consulta direta ao pgvector;
- chamada direta ao OpenAI/Gemini/Anthropic;
- lógica de autorização de tool.


Fluxo HTTP esperado:


```text
HTTP Request
  ↓
Api
  ↓
Application
  ↓
Runtime / abstrações
  ↓
Providers + Infrastructure
```


## Grafo de dependências permitido


A direction principal deve ser:


```text
Api
 ├── Application
 ├── Contracts
 ├── Infrastructure
 ├── Providers
 ├── Runtime
 └── Observability


Application
 ├── Domain
 ├── Contracts
 └── abstrações do Runtime


Runtime
 ├── Domain
 └── Contracts quando necessário


Providers
 ├── Runtime/abstrações
 └── Domain somente quando necessário


Infrastructure
 ├── Domain
 ├── Application abstractions quando necessário
 └── Contracts


Observability
 └── contratos internos mínimos


Domain
 └── nenhuma dependência de infraestrutura
```


A Api pode conhecer implementações concretas apenas para registrá-las na injeção de dependência. Isso não significa que possa executar lógica diretamente nelas.


## Dependências proibidas


Proibir explicitamente:


```text
Domain -> Infrastructure
Domain -> Providers
Domain -> Semantic Kernel
Domain -> EF Core
Application -> OpenAI SDK
Application -> Gemini SDK
Application -> Anthropic SDK
Application -> RabbitMQ Client
Application -> DbContext
Contracts -> Infrastructure
Contracts -> Providers
Serviço de negócio -> provider de IA diretamente
```


## Composition Root e Dependency Injection


A composição das implementações concretas deve acontecer na Api.


Exemplo conceitual:


```csharp
services.AddHarnessApplication();
services.AddHarnessRuntime();
services.AddHarnessSemanticKernelRuntime();
services.AddHarnessProviders(configuration);
services.AddHarnessInfrastructure(configuration);
services.AddHarnessObservability(configuration);
```


Cada projeto de infraestrutura pode fornecer seu próprio método de extensão de DI.


O restante do código trabalha com interfaces.


## Multi-tenancy


TenantId é obrigatório em qualquer operação que acesse configuração, memória, execução, tools ou dados persistidos pelo Harness.


Nenhum repository deve possuir método operacional ambíguo como:


```csharp
GetAgentConfiguration(agentId)
```


quando a informação puder variar por tenant.


Preferir:


```csharp
GetAgentConfiguration(tenantId, agentId)
```


Toda consulta de memória vetorial deve aplicar isolamento por tenant antes da recuperação semântica.


Não aceitar filtragem de TenantId apenas depois de consultar os embeddings.


## Agent Registry


O Agent Registry deve conhecer a definição lógica dos agentes disponíveis.


Separar:


```text
AgentDefinition
        ↓
TenantAgentConfiguration
```


AgentDefinition define a capacidade global.


TenantAgentConfiguration define como aquela capacidade opera para um tenant específico.


Exemplo:


```text
AgentDefinition
AgentId = cartorio.cancelamento-protesto
DefaultModelPolicy = balanced


TenantAgentConfiguration
TenantId = X
AgentId = cartorio.cancelamento-protesto
Enabled = true
ModelPolicy = high-reasoning
AllowedTools = [...]
KnowledgeBaseId = ...
```


## Tool Registry


Tools são capacidades controladas pelo Harness, não métodos livres que o LLM pode executar.


Cada ToolDefinition deve possuir no mínimo:


```text
ToolId
Name
Description
InputSchema
RiskLevel
RequiresTenantContext
Timeout
```


Antes de executar uma tool, validar:


```text
Tenant
  + Agent
  + Tool
  + Policy
  + ExecutionContext
```


Se uma dessas validações falhar, a tool não é executada.


## Serviços verticais


Cartório, imobiliária, CRM, ERP, cobrança e demais verticais não devem ser incorporados à solution do Harness como regras internas.


Exemplo recomendado:


```text
NextAZ.Harness
        ↓ via HTTP/event/tool contract
NextAZ.Cartorio
```


O serviço de Cartório continua proprietário de:


- protestos;
- pedidos;
- certidões;
- regras cartorárias;
- estados do pedido;
- validações determinísticas do domínio.


O Harness possui somente uma tool/adaptador autorizado para solicitar uma operação ao serviço de Cartório.


O mesmo padrão deve ser aplicado aos demais domínios.


## RabbitMQ


Mensageria deve usar contratos estáveis de integração.


Eventos devem incluir quando aplicável:


```text
MessageId
CorrelationId
TenantId
OccurredAt
EventType
SchemaVersion
```


Consumers não devem duplicar lógica de Application. O consumer recebe a mensagem e encaminha para um caso de uso.


Exemplo:


```text
RabbitMQ Consumer
      ↓
Application Use Case
      ↓
Harness orchestration
```


## Banco de dados e migrations


O Harness deve possuir banco ou schema logicamente isolado dos demais módulos.


Se inicialmente estiver no mesmo cluster PostgreSQL da NextAZ, manter ownership separado e migrations exclusivas do Harness.


Regras:


- Harness não faz join direto com tabelas de CRM, ERP ou Cartório;
- integrações de domínio devem ocorrer por contrato/API/evento;
- ExecutionId e TenantId devem ser indexados nas tabelas de execução;
- dados de memória devem possuir TenantId obrigatório;
- configurações devem ser versionáveis.


## Testes obrigatórios


### Domain.Tests


Testar invariantes puras, IDs, policies e regras internas.


### Application.Tests


Testar casos de uso usando mocks/fakes das abstrações.


Cenários mínimos:


- tenant inexistente;
- agente desabilitado;
- agent resolution com sucesso;
- tool não autorizada;
- provider indisponível com fallback;
- isolamento entre tenants;
- falha no runtime;
- correlation id preservado.


### Runtime.Tests


Testar Agent Resolver, Model Router, Tool Registry e policy evaluation sem depender de API externa real.


### IntegrationTests


Testar:


- PostgreSQL;
- pgvector;
- RabbitMQ;
- DI completo;
- execução end-to-end com provider fake/stub.


Não tornar testes automatizados dependentes de saldo real de API de LLM.


## Estrutura de namespaces


Manter namespaces alinhados ao projeto e responsabilidade.


Exemplos:


```text
NextAZ.Harness.Domain.Agents
NextAZ.Harness.Domain.Tools
NextAZ.Harness.Domain.Executions
NextAZ.Harness.Application.Executions
NextAZ.Harness.Runtime.Agents
NextAZ.Harness.Runtime.Routing
NextAZ.Harness.Runtime.Tooling
NextAZ.Harness.Infrastructure.Persistence
NextAZ.Harness.Infrastructure.Memory
NextAZ.Harness.Infrastructure.Messaging
NextAZ.Harness.Providers.OpenAI
NextAZ.Harness.Providers.Gemini
```


Evitar namespaces genéricos como Helpers, Utils ou Common para regras importantes.


## Regras para o Codex


Ao implementar esta solution, o Codex deve:


1. criar os projetos e referências seguindo o grafo de dependências deste documento;
2. não introduzir provider de IA diretamente em Domain ou Application;
3. não introduzir Semantic Kernel como contrato público;
4. criar interfaces antes das implementações externas;
5. manter TenantId obrigatório em operações multi-tenant;
6. manter AgentId independente de modelo/provider;
7. manter serviços verticais fora do core do Harness;
8. usar DI para implementations concretas;
9. não criar classes Helpers/Utils como atalho arquitetural;
10. manter async/await e CancellationToken nas operações I/O;
11. propagar CorrelationId e ExecutionId;
12. não armazenar secrets no código-fonte;
13. criar testes para boundaries críticos;
14. não permitir acesso direto a banco de outro domínio;
15. não permitir execução de tool sem autorização explícita.


## Critério de aceite arquitetural


A arquitetura está correta quando for possível realizar trocas como estas sem alterar Domain e com impacto mínimo em Application:


```text
Semantic Kernel -> outro runtime
OpenAI -> Gemini
Gemini -> Anthropic
pgvector -> outro mecanismo de memória
RabbitMQ -> outro broker
```


Também deve ser possível adicionar uma nova vertical, como Cartório ou Imobiliária, sem copiar o core de IA.


A nova vertical deve registrar agentes, tools, policies e contratos de integração e reutilizar o mesmo Harness.
